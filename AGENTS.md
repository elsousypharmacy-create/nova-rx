# AI Agent Instructions — NOVA Rx

These instructions apply to every AI agent operating in this repository. Owner decision 2026-11-11: **only two Claude sessions work on NOVA Rx.** ChatGPT, Gemini, Kimi and Grok are out of the process (their old instructions are archived in `docs/archive/retired-agents/` and are not active).

**MANDATORY BOOT ORDER (cheap first).** (1) Read this `AGENTS.md`. (2) Read `CURRENT.md` (60 lines max) and check its P0 incidents across both `nova-rx` and `pharmacy`. If nothing changed for your assigned work, report IDLE and stop. (3) Read only your relevant `HANDOFF.md` section (search the Issue/PR number or the last 60 lines), `docs/skills/nova/SKILL.md`, and the comments on Issue #87 since your last checkpoint. Check the current claim, PR, CI and deployment state before editing. (4) Read `docs/ERP_MASTER_PLAN.md` and `reports/erp-roadmap.json` only when acceptance criteria, dependencies or scope require them. (5) Re-read Issue #87 immediately before every claim and before the first edit; on a collision the earlier claim wins and the other agent withdraws. (6) Update `CURRENT.md` in the same reviewed PR when project state changes, preserving the full `HANDOFF.md` history. GitHub comments and skill files do not launch sessions and do not prove that an agent received anything.

**Roles.** *Claude 2 = lead manager and reviewer:* priorities, assignment, PR sequencing, merges after the gates, roadmap and CURRENT accuracy, independent review of Claude 1's work. *Claude 1 = lead implementer:* CAT, INV, POS and SEC-03 lanes. Every task has exactly one accountable claimant from claim to merged-and-verified. **Author ≠ reviewer, and nobody merges their own work.** Both agents are the same model family, so review independence is weaker than between different vendors: compensate with exact-SHA reviews, re-run tests, mutation checks of the tests, and the owner-only gates below. Never infer a running session from old comments.

**One source of work.** GitHub Issues are assignments; PRs are artifacts. Record one accountable agent, scoped files, acceptance checks, claim/checkpoint and the exact next action in the Issue. Maximum **three** active implementation PRs (docs/roadmap PRs are counted separately, at most one open). No overlapping edits without explicit coordination.

**Definition of done.** CLAIM → implement test-first → CI (a new workflow only runs once it is on the default branch or on a PR) → independent review of the exact head SHA → resolve findings → merge after the gates → verify. CODE_PUSHED, CI_PASS, REVIEWED, MERGED, INTEGRATED, DEPLOYED, LIVE_VERIFIED and ACCEPTED are different states; merged pure code is never «accepted». Never claim untested behaviour as PASS.

**Owner-only (never without his specific approval, never inferred from urgency):** real supplier cart writes/orders/checkout, payments, secrets or credential changes, **unlocking or force-releasing an unknown (fail-closed) supplier operation** (only through the evidence-based reconciliation path in `docs/procurement/SUPPLIER_OPERATION_RECONCILIATION_DESIGN.md`, with his approval), production deploy, destructive migrations or deletions, choosing the storage product, spending money. When one is needed: stop only that action, document it in Issue #87, continue all safe work. Do not contact the owner for routine questions or progress; report completion once, with evidence.

**Mandatory checkpoint.** After each meaningful batch and before exit, post on Issue #87: task ID, owner, branch/PR/SHA, tests with commands and results, CI, reviewer verdict, what is NOT tested, blockers, next action; append the same to `HANDOFF.md` through a PR. Re-read the latest `HANDOFF.md` first. Never expose secrets or customer data in GitHub.

**Roadmap.** Issue #87, `docs/ERP_MASTER_PLAN.md` and `reports/erp-roadmap.json` define acceptance (17 stages × 5 tasks); the sanitized public mirror lives in the `pharmacy` repo (`nova-status.json`, rendered by `nova-monitor.html`) and must stay consistent. Accepted = status `verified` with evidence, `verifiedAt` and a verification record. Scope or weight changes need `planVersion` and a changelog entry.
