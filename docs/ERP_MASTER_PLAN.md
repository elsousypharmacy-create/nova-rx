# NOVA Rx — خطة ERP التنفيذية ERP-1.0

تاريخ خط الأساس: 9 نوفمبر 2026 — Asia/Riyadh. المالك: أحمد السوسي. [المتابعة #87](https://github.com/elsousypharmacy-create/nova-rx/issues/87). هذه مواصفات ومعايير قبول؛ ليست شهادة أن الميزات تعمل.

## الرؤية والنطاق
ERP عملي لصيدلية السوسي، ثم منتج تجاري متعدد الصيدليات والفروع. العربية وRTL أولًا، الإنجليزية مدعومة، تابلت Xiaomi Pad 5 بالعرض 1280×800، iPhone وكمبيوتر. السرعة ودقة الرصيد والمال أهم من كثرة الشاشات. واجهة Orders بالداشبورد مستقلة عن واجهة NOVA، مع خدمات مشتركة بعقود واضحة. لا تُستبدل بيانات STOCK LIVE أو التشغيل الحالي إلا بخطة ترحيل واعتماد.

## العمل بين Claude وChatGPT
- Claude: تنفيذ الكود وPRs وترحيل البيانات والتوثيق التشغيلي؛ مهمة صغيرة واحدة نشطة في الدورة، بمعرف ثابت من الخطة.
- ChatGPT: مراجعة المتطلبات والكود والأدلة وحالات الفشل؛ يراجع نتائج الاختبارات ويثبت ما شُغّل بالفعل؛ لا يرفع نسبة القبول لمجرد نجاح CI.
- أحمد: الأولوية والسياسة التجارية والقبول على الأجهزة والطابعة والموافقة على أي تكلفة أو طلب شراء حقيقي. لا حاجة لمقاطعته لقرارات تنفيذ روتينية ضمن النطاق المصرح.
- لا تُرسل مهام تلقائيًا لـKimi/Grok/Gemini. Claude يقرأ AGENTS وHANDOFF والخطة والحالة قبل العمل.
- لكل ID: Issue تنفيذ عند بدء العمل، PR/commit SHA، اختبار مناسب، دليل تشغيل، عيوب ومحدوديات، مراجع وتاريخ. حدّث HANDOFF والـJSON الخاص والنسخة العامة بعد كل دفعة. لا تترك ادعاء نشر إذا لم تنجح عملية النشر.

## المعمارية وحدود البيانات
- واجهة خفيفة بمكونات موحدة ووظائف مجال قابلة للاختبار؛ خدمات API ذات إصدارات؛ SQL معاملاتي للمبيعات والمخزون والمال. اختيار المنتج النهائي ADR مطلوب في FND-02 بعد قياس، وليس قرارًا مفترضًا في هذه الوثيقة.
- Worker بوابة API وعزل أسرار وتكاملات. KV مناسب لجلسات/كاش، ولا يُعتمد منفردًا كدفتر معاملات مالي/مخزون.
- تخزين ملفات خاص بمفاتيح نطاق ووقت صلاحية؛ queue للأعمال البطيئة؛ outbox للأحداث المرسلة بعد commit؛ webhooks موقعة مع dedup.
- الكيانات الأساسية: Tenant, Branch, User, Role, Customer, Supplier, Seller, Product, Barcode, UnitConversion, Batch, StockMovement, Reservation, Invoice, InvoiceLine, Payment, Refund, PurchaseOrder, GoodsReceipt, SupplierInvoice, JournalEntry, JournalLine, Shift, Expense, Delivery, AuditEvent, SyncOutbox.
- tenantId إلزامي مع branchId حيث يلزم؛ مفاتيح مستقرة لا تعتمد الاسم؛ createdAt/updatedAt/actor/version. unique على invoice number داخل نطاقه وidempotency key داخل العملية. كل تاريخ داخلي UTC، والعرض حسب الفرع؛ يوم تشغيل الصيدلية يعبر منتصف الليل وفق سياسة موثقة.
- المال decimal ثابت أو أصغر وحدة نقدية، لا floating arithmetic غير مضبوط؛ rounding موحد. مجموع الدفعات يطابق المستند، مجموع مدين=دائن، مجموع ledger stock يطابق الرصيد، المرتجع لا يتجاوز الأصل. الحركة النهائية تُعكس ولا تُحذف.
- بروتوكول الكتابة: تحقق الجلسة والصلاحية والمدخلات→تحقق version/idempotency→transaction لحفظ المستند والدفع والمخزون والقيد→commit→outbox. إعادة نفس المفتاح تعيد النتيجة نفسها؛ نفس المفتاح بمحتوى مختلف يرفض.
- المصدر الحالي ومصدر NOVA لا يكتبان نفس المعاملة دون بروتوكول ملكية واضح. migration: نسخة خاصة→dry run→تقرير فروق→cutoff→موافقة→ترحيل→مطابقة→نافذة رجوع.

## تدفقات قبول عابرة للوحدات
1. مسح باركود→وحدة صحيحة→حجز تشغيلة FEFO→تحقق خصم→دفع→commit ذري→إيصال؛ عند timeout يُستعلم عن نفس المفتاح قبل إعادة الدفع.
2. نقص من Orders→مطابقة عبوة→اختيار مخازن Aumet/PO→توزيع يدوي أو اقتراح قابل للتعديل→مراجعة مجموعات→إضافة سلة مؤكدة read-back→تأكيد بشري للطلب→استلام جزئي→فاتورة مورد وقيد.
3. مرتجع مرتبط بالأصل→كمية وتشغيلة صالحة→رد مال→عكس مخزون/تكلفة/نقاط/قيد→إيصال ومراجعة.
4. انقطاع→أسعار snapshot مؤرخة→فاتورة مؤقتة UUID→مزامنة outbox→تعارض في قائمة مراجعة؛ لا نجاح صامت ولا ازدواج بيع.
5. إقفال وردية→نقد متوقع مقابل معدود→فروق وأسباب→اعتماد→إقفال الفترة المحاسبية مع قفل التعديل.

## ترتيب التسليم والبوابات
- G0: FND + SEC + CAT، تثبيت مصادر البيانات وقرار التقنية وعزل الوصول. UX والأداء والاختبارات تبدأ من اليوم الأول؛ التبعيات أدناه بوابات قبول التكامل النهائي، لا تأجيل تصميم الواجهة.
- G1: INV + POS + OFF للفرع الأول مع مطابقة ومعاملات واستعادة؛ لا استبدال POS القديم قبل قبول الفرع.
- G2: BUY + CRM + FIN، ثم OPS/MSG/BI وCLN بتدرج ومراجعة صيدلي.
- G3: INT + UX + QA وتجربة حقيقية وخطة رجوع.
- G4: SAAS، عزل وتكلفة ودعم وعميل ثانٍ قبل إعلان الجاهزية للبيع.
- التقدير الزمني لا يُثبت الآن؛ بعد FND-01 وFND-02 تسجّل كل مهمة حجمًا وتقديرًا ونطاق ثقة وتاريخًا متوقعًا، ثم يحسب forecast من سرعة العمل الفعلية. لا تاريخ انتهاء مختلق.

## الحالات والنسب
queued / in_progress / for_review / blocked / verified. blocked له سبب ومسؤول وفك حظر. verified لا يُقبل إلا مع evidence غير فارغ وverifiedAt وverification.reviewer ونتيجة مراجعة pass. لا تُحوّل done القديمة تلقائيًا.

نسبة المرحلة = أوزان البنود المقبولة ÷ جميع أوزان بنود المرحلة. نسبة الخطة = Σ(وزن المرحلة × نسبتها) ÷ Σأوزان المراحل ×100. الأوزان وحدات نسبية مجموعها 109، وتُطبع النتيجة كنسبة من 100. البنود داخل كل مرحلة متساوية مبدئيًا؛ تغيير الوزن أو النطاق يستلزم planVersion وسجل سبب وتاريخ وتغير المقام. النسبة عدد البنود المقبولة وفق المتطلبات، وليست ساعات العمل المتبقية أو نسبة كود مكتوب.

خط الأساس: 0/85 قبول نهائي مسجل؛ تسعة بنود لها أعمال سابقة للمراجعة. هذا لا يعني أن الكود الحالي صفر. HANDOFF مرجع تاريخي، ويلزم مطابقة أدلته بالمعايير الجديدة. لا نخترع نجاح واتساب أو طابعة أو سلة مورد أو هوامش مالية.

مثال بند مقبول:
```json
{"status":"verified","evidence":[{"url":"https://github.com/owner/repo/actions/runs/123","kind":"test","sha":"commit SHA"}],"verifiedAt":"ISO timestamp","verification":{"reviewer":"ChatGPT","result":"pass","ownerAcceptance":"reference when required"}}
```
