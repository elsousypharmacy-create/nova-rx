# FND-04 — ملاحظات عقود API (مسودة للمراجعة)

البند: FND-04 من [ERP_MASTER_PLAN.md](../ERP_MASTER_PLAN.md) · المتابعة [#87](https://github.com/elsousypharmacy-create/nova-rx/issues/87) · التفويض [#104](https://github.com/elsousypharmacy-create/nova-rx/issues/104) · العقد: [FND-04_API_CONTRACT.yaml](FND-04_API_CONTRACT.yaml).

**الحالة: DRAFT — توثيق عقود فقط، بلا أي تنفيذ.** معيار قبول البند: «OpenAPI للقراءة والكتابة؛ أخطاء عربية برمز ثابت وrequestId؛ pagination ومهلات وإعادة محاولة آمنة وidempotency للكتابة». حالة البند في `reports/erp-roadmap.json` تبقى `queued` ولم تتغير.

## 1. كيف تُقرأ المسودة
- كل عملية موسومة `x-nova-status`: ‏`current` (موجود فعلًا في `worker/procurement/provider/http.js` على `main` وموثق كما هو مقروء، بلا تجميل) أو `proposed` (مقترح لـ ERP v1 — **لم يُنفذ أي سطر منه** ولا يُقرأ كالتزام تشغيلي).
- العلاقة بـ FND-03: الكيانات والحالات والثوابت في `proposed` مأخوذة من [FND-03_DOMAIN_MODEL.md](FND-03_DOMAIN_MODEL.md) **بصيغته المسودة بعد تصحيحات المراجعة (PR ‏#108) — مسودة غير معتمدة بعد**. انظر حدود التبعية في §5.

## 2. current — ما هو موثق من الكود الحي
| السمة | الحالة في الكود المقروء |
|---|---|
| المصادقة | `X-Nova-Pin` للتطبيق و`X-Ingest-Secret` للاستقبال؛ مقارنة constant-time بعد تجزئة الطرفين؛ غياب السر = ‏503 not-configured (فشل مغلق) |
| حد المعدل | 40 بحثًا/دقيقة (429 + Retry-After)؛ محاولات مصادقة فاشلة ≤ 8/دقيقة (429 too-many-attempts) |
| الأخطاء | مغلف `{error: code}` بسيط **بلا requestId** — فجوة موثقة مقابل معيار القبول |
| المهلة | 45 ثانية على استدعاء مصدر المخزون الخارجي فقط (`/api/purchases/stock`)؛ لا مهلة موثقة لمسارات الموردين الأخرى في الملف المقروء — **[غير مختبر]** |
| idempotency | عمليات السلة/الطلب ذرية عبر سجل D1 (`NOVA_PURCHASE_OPS`، scope فريد للعملية النشطة) — **لكن لا توجد ترويسة Idempotency-Key للعميل**؛ إعادة المحاولة الآمنة عبر ‏`status` لا عبر مفتاح عميل |
| pagination | غير موجود (لا قوائم طويلة في current) |

## 3. proposed — قرارات التصميم المقترحة (للمراجعة)
1. **الإصدار:** مسار `/api/v1/...` ثابت؛ الكسر غير المتوافق = ‏`/v2` جديد، والإصلاحات المتوافقة (حقل اختياري جديد) لا تغيّر الإصدار.
2. **الأخطاء:** مغلف `{error:{code, message, messageEn, requestId, details}}` — عربي أولًا، code ثابت لا يتغير بين الإصدارات الفرعية، requestId في كل استجابة (نجاح أو فشل) ويربط بسجل التدقيق SEC-04.
3. **pagination:** مؤشر opaque (`cursor` + `limit≤200`)؛ لا offsets قابلة للانزياح أثناء الكتابة.
4. **idempotency:** ترويسة `Idempotency-Key` إلزامية لكل كتابة مالية/مخزنية؛ نفس المفتاح + نفس المحتوى = نفس النتيجة، ومحتوى مختلف = ‏409 content-conflict (ثابت FND-03 §4).
5. **content-conflict:** `If-Match` على version/ETag للمستندات القابلة للتعديل (draft)؛ عدم التطابق = ‏409 برسالة عربية توضح أن مستخدمًا آخر عدّل المستند.
6. **المهلات وإعادة المحاولة:** عند timeout في post الفاتورة يُستعلم بنفس المفتاح قبل إعادة الدفع (تدفق القبول 1) — لا ازدواج بيع ولا نجاح صامت. قيم المهلات الرقمية لـ v1 تُثبت عند التنفيذ وليست موثقة هنا.
7. **المشتريات:** مسارات `proposed` للـPO/GRN **تكمل ولا تستبدل** عقود current التشغيلية (سلة/طلب المورد)؛ الدمج بينهما قرار معماري عند BUY-05 (الكيان المالي الداخلي مقابل تكامل المورد الخارجي).

## 4. التحقق المنفذ فعلًا
- `yaml.safe_load` على `FND-04_API_CONTRACT.yaml` → صالح (فحص صياغة؛ 16 مسارًا: 9 current + 7 proposed).
- مراجعة اتساق يدوية: مسارات current مطابقة لمجموعة `ROUTES` في `worker/procurement/provider/http.js`؛ كيانات/حالات proposed مطابقة لمسودة FND-03 المصححة (بما فيها goodsReceipt وpartiallyReceived المشتقة).
- **NOT TESTED:** لا تنفيذ ولا خادم ولا اختبار تكامل؛ الملف وثيقة تصميم فقط. لم تُقرأ عقود `supplier-orders.js`/`supplier-cart-service.js` الداخلية (خارج الملفات المسموحة في هذه الدورة) — تفاصيل حقول طلبات/استجابات عمليات السلة والطلب موثقة على مستوى السلوك من موجه `http.js` فقط.

## 5. حدود التبعية وأسئلة التكامل (FND-03 غير معتمدة بعد)
1. FND-03 ما زالت مسودة قيد المراجعة (PR ‏#108)؛ لو اتغيرت الكيانات/الحالات عند الاعتماد، تُراجع هذه العقود بنفس الجولة — **لا يُبنى تنفيذ على هذه المسودة قبل اعتماد FND-03**.
2. `taxClass` في الفاتورة/الصنف موسوم غير محسوم (CAT-03، FND-03 §7) — العقد يمرره كنص بلا enum ملزم.
3. تمثيل المال `Money` كنص decimal — التمثيل النهائي مع قرار FND-02 (FND-03 §7-2).
4. مصادقة v1 المقترحة (حسابات فردية بدل PIN) تُوثق في SEC-01 — العقد لا يفترض آلية بعد، وترويسة PIN الحالية موثقة كما هي فقط في current.
5. هل تُستوعب عقود current للمشتريات تحت `/api/v1/procurement/...` أم تبقى مسارات تشغيلية منفصلة بعقدها الحالي؟ (مرتبط بقرار BUY-05 وFND-05 §8-7).

## 6. قرارات مفتوحة
1. شكل مفتاح idempotency المعروض للعميل (UUID أم مفتاح مستند مركب) — يُحسم مع التنفيذ.
2. قيم المهلات وحدود المعدل لـ v1 بالأرقام (قياس UX-03/04 قبل التثبيت).
3. هل requestId يولد عند البوابة فقط أم يُقبل من العميل مع تحقق الصيغة؟
4. سياسة إهمال (deprecation) عند الانتقال بين الإصدارات ومدة دعم v1 بعد v2.
